# Pi Alehouse contributor guidance

This is one Nix-free source package. Root `node_modules` holds development dependencies; `harness/src`, `harness/test`, and `harness/docs` are internal. `extensions/`, `lib/`, and `permission-system/` are internal integrations; `resources/` is source input; `runtime/{agents,policy,permission-system}` is generated matched output. The explicit CLI is `bin/pi-alehouse.mjs`; root `pi.extensions: []` means Pi does not autoload `composition.ts` or treat this as a `pi install` extension.

Keep Owner lifecycle in the harness core, Pi SDK adaptation in runtime, authorization in the managed permission system/policy, and UI as projections only. Preserve existing tool names, profile IDs, `harness:*` records, on-disk config paths, lifecycle event names and `Symbol.for` keys as compatibility contracts, even where names contain `pi-harness` or `@rocklee`. Do not copy credentials, replace existing user files, silently enable models, weaken denies, or claim OS sandboxing. Initialize only missing user resources by explicit command; routing defaults to `off`.

From the root use `npm ci --ignore-scripts` (including pinned development Pi SDK), `npm run build`, then `npm run check`. Only install a verified **built tarball** in production with `--omit=dev --legacy-peer-deps --ignore-scripts` so dependency peers cannot auto-install a second Pi runtime; host Pi remains separately supplied. Run portable policy and controlled host suites separately when provided; never execute real-model, network, human-approval, or publishing workflows without explicit authorization. Do not treat inherited 801 tests, fixture exit codes or local observations as public release acceptance. Generated output, reports, secrets, and private transcripts are not source. Source build should retain the upstream license in generated permission-system output. See `harness/docs/development.md`, `harness/docs/security.md`, and `harness/docs/limitations.md` before changing contracts.
